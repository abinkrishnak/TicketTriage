# Milestone 1 plan versus delivered prototype

The original goal was to help Raj, a Tier-1 e-commerce support employee, find verified guidance faster while retaining responsibility for the final response. The delivered artifact investigates that goal through separate component tests and an offline evidence demo. It does not demonstrate that Raj works faster.

The original Milestone 1 problem statement, dated 23 August 2026, was reviewed from retained development extraction `.private_audit/087.txt` (pages 1–2). That private source is not redistributed. The table paraphrases project commitments without reproducing course forms or personal identifiers. “Why changed” describes recorded design reasoning or an explicit final tradeoff, not an invented contemporaneous user study.

| Original plan | Final implementation | Why changed | Consequence |
|---|---|---|---|
| Remove names, emails, postal codes and identifiers before API use; own redacted ticket data | Public synthetic Bitext, fictional policy cards and generalized experience-inspired queries; limited credential/privacy checks, not comprehensive automated redaction | Data minimization and the fictional/generalized boundary limited what was sent in the bounded experiment | Redaction automation was not delivered; arbitrary real tickets are not shown safe for vendor submission |
| Apply a confidence/abstention threshold when evidence is weak | Explicit candidate selection, finite scope/state checks, evidence validation and mandatory review; no calibrated retrieval/classifier confidence threshold | Uncalibrated probabilities and similarity scores do not establish eligibility; a threshold would require separate validation rather than final-test tuning | No measured confidence-based rejection performance; novel unsupported wording can still be mishandled |
| Own a FAISS or Chroma vector store | In-memory cosine ranking across all 15 intact cards, with saved embeddings | Initial technical guidance selected NumPy search for the small corpus; a vector database was unnecessary at this scale | Simpler inspectable implementation; no indexing/scalability benchmark |
| First test extraction in the OpenRouter playground, then build Python workflow | Saved evidence supports a locked Python Chat Completions experiment using OpenRouter/OpenAI routing, strict schemas and recorded usage | Code enabled repeatable settings, fixed cases, bounded cost and evidence capture | No saved playground experiment was located; do not claim one occurred or that a prompt exploration study was performed |
| At least 85% policy Recall@1 | Measure TF-IDF first: 35/60; semantic result later 38/60 | Professor feedback called for an improvement over a measured baseline instead of an unsupported absolute target | Original 85% ambition was replaced, not achieved; show the drift openly |
| Compare semantic retrieval against a lexical baseline; baseline-relative gap not yet set | +10 percentage points selected after observing the aggregate TF-IDF baseline, before semantic scoring: target 41/60 | Six net additional correct top results defined a sample-level engineering objective | Actual +5 points missed the goal; target was not preregistered before baseline analysis |
| A redacted ticket → predicted intent → retrieved card → agent-reviewed response; initially validate an end-to-end slice | App replays saved GPT evidence; optional local new-ticket classifier/retrieval preview; no live GPT draft mode | Reliable offline demonstration avoids fresh spend and preserves inspectable outputs; observed top-1 errors favor visible candidates and human selection | Delivered scope is narrower than an arbitrary-ticket end-to-end assistant; productivity, selection accuracy and friction remain unmeasured |
| A fixed workflow, no automatic support-system decisions or actions | No autonomous agent, CRM/refund/cancel/write tool, account access or customer sending | Human accountability and bounded academic scope were retained | No autonomous action capability or agent success metric; this boundary is continuity, not a late agent removal |
| Author 12–15 policies, with warranty among proposed topics | Fifteen short cards across six categories; no general warranty card, and later-life warranty issues are excluded by the damaged-item card | Approved taxonomy narrowed the domain to explicit support-state distinctions | Limited coverage; not a general retailer knowledge base |
| “Own evaluation, logging and abstention checks” | Saved experimental outputs/usage and local diagnostic replay; no persistent production telemetry | Offline assessment emphasized evidence retention and finite control checks | Logs demonstrate auditability of experiments, not ongoing operational monitoring |

The classifier config records `tuning: none`; semantic retrieval used one approved model/configuration. Changing max sequence length from 256 to 512 was a pre-score token-fit decision, not a scored length search. The baseline and its errors were already known. Stage 8 used one model and one prompt per task; it did not demonstrate multi-model optimization. Guardrails intentionally used known failures as development evidence. These are different kinds of design exposure, not one blanket claim of “no tuning.”
